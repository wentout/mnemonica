# mnemonica — usage skill for agents

mnemonica is a JavaScript runtime library for **modelling data as lineage**:
each type is constructed from an instance of its parent, so every object
carries the story of how it came to be — who it came from, with which
arguments, in which order.

## When to use

- The code imports `mnemonica` or `@mnemonica/*`
- The task declares types (`define()`, `lazy()`, `@decorate()`) or
  constructs instances
- TypeScript complains about a mnemonica constructor or subtype — see
  **NEVER cast** below before touching anything

## The model

`define(name, handler)` declares a type and returns its constructor.
A subtype is declared on its parent type and constructed **from a parent
instance**: `new parent.Child(args)`. The child's prototype chain runs
through the parent instance — it inherits the parent's data, and
`instanceof` answers every ancestor. Construction context (arguments,
parent, type) is readable with `getProps(instance)`. Do not copy parent
fields into the child by hand; the chain already carries them.

mnemonica is a **runtime** library: `define()` registers types as a side
effect, into one type graph, whatever style declared them. TypeScript
cannot see a graph built by runtime calls — the two lineages below are the
two ways to make it sound for TypeScript.

## Rule zero: reach every constructor through `lookup()`

Get constructors with `lookup()` — never by importing them from a model
file, never by casting. Which `lookup` depends on the lineage:

| Lineage | Call | Typed from |
|---|---|---|
| Builder | `App.lookup('User.Admin')` | the builder value's own registry |
| Builder | `User.lookup('Admin')` on a type's own constructor | the builder registry; resolves **relative first** (its own subtypes), then the same string as an absolute path from the root |
| Tactica | `lookup('User.Admin')` — the free function | the global `TypeRegistry`, generated by tactica |

Paths are dot-separated nested names — the same strings everywhere.
**The builder has no free-function style**: it is `App.lookup` /
`Type.lookup` only. The free `define` / `lookup` and `@decorate()` are
what tactica exists for.

## Lineage 1 — Builder (no tooling)

Chain `.define()` on the exported `mnemonica` object or on a
`createTypesCollection()` (an isolated collection). The returned value
carries a local registry, so everything is typed with no build step.

```typescript
import { mnemonica } from 'mnemonica';

interface UserShape { name: string }
interface AdminShape extends UserShape { role: string }

export const App = mnemonica
	.define('User', function (this: UserShape, data: { name: string }) {
		this.name = data.name;
	})
	// names given to a constructor's .define() are relative to it
	.define('Admin', function (this: AdminShape, data: { role: string }) {
		this.role = data.role;
	});

const User = App.lookup('User');
const user = new User({ name: 'Ada' });
const admin = new user.Admin({ role: 'root' }); // admin.name === 'Ada'
```

Across files: export the chain and continue it where needed
(`export const Admin = User.define('Admin', …)`); the registry rides in
the value's type. Keep imports tree-shaped — no cycles.

The builder cannot type `@decorate()` classes (a class decorator never
changes the class binding's type) and cannot type the free `lookup()`.
For those, use tactica.

## Lineage 2 — Tactica (codegen + declaration merging)

For `@decorate()`, the free `define` / `lookup`, or a codebase with free
`define()` calls everywhere. Tactica scans your code and generates the
`TypeRegistry` augmentation; TypeScript merges it into mnemonica's
declarations. **Declaration merging only works when both steps are done:**

| MUST | Why |
|---|---|
| Run `npx tactica` (or `npx tactica --watch`) after changing any `define()` / `@decorate()` | `.tactica/registry.ts` is what types `lookup()`; a stale file means stale or missing types |
| Add `.tactica/**/*` to `tsconfig.json` `include` | without it the augmentation is invisible and `lookup()` silently falls back to `TypeClass \| undefined` — the most common failure |

```json
{
	"include": ["src/**/*", ".tactica/**/*"]
}
```

```typescript
import { define, lookup } from 'mnemonica';

define('User', function (this: UserShape, data: { name: string }) {
	this.name = data.name;
});
define('User.Admin', function (this: AdminShape, data: { role: string }) {
	this.role = data.role;
});

const User = lookup('User');                  // typed by .tactica
const user = new User({ name: 'Ada' });
const admin = new user.Admin({ role: 'root' });
```

- **Runtime values** → `lookup('Name')`. **Type annotations** →
  `import type { User, User_Admin } from '../.tactica/types'`.
- Never edit `.tactica/` — change the `define()` call and regenerate.
- `InstanceType<typeof X>` aliases belong only inside the model
  definition files themselves; everywhere else use `.tactica/types`.
- `@decorate()` declares a root type, `@decorate(User)` a subtype of
  `User`; reach them the same way, `lookup('User.Admin')`. See
  [docs/decorate.md](./docs/decorate.md).

## NEVER cast

**NEVER write `as unknown as`, `as any`, or `new (instance as any).Child(…)`
on mnemonica types.** Both lineages type everything; a cast only hides why
the types are missing.

If you feel you need one: **stop and ask the user**, explaining what
fails and that constructors must come from `lookup()`. The cause is
almost always one of:

1. tactica was not re-run after the types changed — run `npx tactica`;
2. `.tactica/` is not in `tsconfig.json` `include`;
3. a constructor is imported from a model file instead of `lookup()`;
4. a subtype is constructed from a constructor, not from its parent
   instance (`new user.Admin(…)`).

## Constructing subtypes

- Subtypes are constructed from a parent instance: `new user.Admin(…)`.
  `new` on a looked-up subtype constructor without a parent instance
  fails at runtime; to attach to an existing instance explicitly use
  `apply(parent, Ctor, args)` / `call` / `bind`.
- `strictChain: true` (default) requires the immediate parent type;
  `strictChain: false` also accepts instances further up the chain.
- A constructor resolved through a getter (circular imports) uses
  `lazy()`: `User.lazy('Guest', () => GuestHandler)`.
- Match the style already in the codebase — `define()` and `@decorate()`
  are runtime equivalents.

## Observability: mnemonica + dive + otel

This is the reason the lineage matters in production. `@mnemonica/dive`
records execution flow over the objects themselves — no
AsyncLocalStorage, no monkey-patching — and `@mnemonica/otel` wires every
mnemonica construction into it and exports OpenTelemetry spans. Together
they give Node.js userland code near-complete observability:

- **Every construction is an edge.** With otel's `attachHooks`, each
  `new` of a mnemonica type is recorded under its data-flow parent — the
  instance **is** the context.
- **A failure carries its story.** An Error thrown in a wrapped call
  carries its flow and its data: `getFlow(error)` and
  `getErrorInstance(error)` work anywhere, including a process-level
  `uncaughtException` handler.
- **Across time.** Wrap timer, queue and emitter callbacks with the
  instance they serve (`dive.wrap(fn, instance)`); a callback that fires
  long after its request finished still reports that request's chain.
- **No retention to tune.** History lives exactly as long as something
  holds it, and is collected after — no buffers to size.

Start here: [@mnemonica/dive](https://www.npmjs.com/package/@mnemonica/dive)
(where to wrap, reading flows) and
[@mnemonica/otel](https://www.npmjs.com/package/@mnemonica/otel)
(`attachHooks`, OpenTelemetry providers). NestJS apps:
